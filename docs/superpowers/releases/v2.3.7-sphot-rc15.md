## Mudanças desde a rc14

**Disparo de templates pela Cloud** (para o NX-CWDash):
- `sendTemplate` com `emitWebhook` e `chatwoot` opcionais;
- quando o cliente responde, o template entra no Chatwoot antes da resposta;
- upload de mídia para a Meta (`POST /business/uploadMedia/{instance}`);
- motivo completo da falha nos status (`errors`, `timestamp`, `conversation`, `pricing`, e `MessageUpdate.errors`).

**Correções:**
- busca da mensagem a cada status com índice (antes varria a tabela);
- status de um mesmo lote da Meta não se perdem;
- com número duplicado, status vão para a dona e respostas para a original;
- mídia enviada por link aparece no Chatwoot;
- a senha do banco não aparece mais no log do start.

## Variáveis de ambiente

- **Nova, opcional:** `CHATWOOT_DISPATCH_CONTEXT_HOURS` (padrão 72).
- **Recomendado (não depende da rc15):** `WA_BUSINESS_VERSION=v25.0`. A v18.0, que vale quando a variável não está definida, expirou em 26/01/2026. Testado na VPS: 8/8 fluxos da Cloud.

## Para quem já usa a API (n8n, sistema de agente)

- Sem as opções novas, envio, eventos e Chatwoot são iguais.
- `MESSAGES_UPDATE` ganha `errors`, `timestamp`, `conversation` e `pricing`. O `error` de hoje continua.
- Status que antes se perdiam num lote passam a ser entregues.
- A instância duplicada de disparo continua funcionando: os status voltam para quem enviou, e as respostas vão para a original.

## Deploy

**Antes da troca de imagem**, no Postgres de produção. Isso evita travar a tabela `Message` no start.

```sql
ALTER TABLE "Message" ADD COLUMN IF NOT EXISTS "dispatchEmitWebhook" BOOLEAN,
  ADD COLUMN IF NOT EXISTS "dispatchChatwoot" BOOLEAN,
  ADD COLUMN IF NOT EXISTS "dispatchSyncedAt" TIMESTAMP;
ALTER TABLE "MessageUpdate" ADD COLUMN IF NOT EXISTS "errors" JSONB;
-- um comando por vez (CONCURRENTLY não roda em transação):
CREATE INDEX CONCURRENTLY IF NOT EXISTS "Message_instanceId_keyId_idx" ON "Message" ("instanceId", ("key"->>'id'));
CREATE INDEX CONCURRENTLY IF NOT EXISTS "Message_dispatch_pending_idx" ON "Message" ("instanceId", ("key"->>'remoteJid'), "messageTimestamp")
  WHERE "dispatchChatwoot" = false AND "dispatchSyncedAt" IS NULL;
-- os dois precisam estar válidos (t); se algum vier f, DROP INDEX e criar de novo:
SELECT indexrelid::regclass, indisvalid FROM pg_index
 WHERE indexrelid::regclass::text IN ('"Message_instanceId_keyId_idx"', '"Message_dispatch_pending_idx"');
```

- As colunas entram na hora (só metadado).
- Os índices não travam gravações. Na VPS, 8 s para 845 MB.
- Se esse passo for pulado, as migrations fazem o mesmo no start com `CONCURRENTLY`. Funciona, mas a Evolution só sobe quando os índices terminarem.

**Troca de imagem:** stop-first, uma réplica. No log, `Applying migration 20261106…` seguido de `Migration succeeded`.

**Conferir depois:**
- envios e respostas pela Cloud e pelo Baileys;
- `Número … está em N instâncias` no log indica números duplicados (informativo).
